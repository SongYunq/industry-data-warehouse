## 设计依据

- Doris 开发环境为单 BE，所有表使用一个 bucket 和 `replication_num=1`，控制 tablet 数量；这不是生产高可用配置。
- 采用 UNIQUE KEY 保障当前数据重跑时幂等覆盖，适合本项目的静态季度快照。
- 四期房源事实约 22,093 行；日历原始明细 8,072,340 行汇总为 344,830 行；评论压缩为 188 个月度行。此规模暂不需要分区。
- 日历表不保留房源×日期的 800 多万条明细；在街区、房型和房屋类型层级预汇总，仍可支持看板筛选。
- 价位用 DECIMAL、坐标用定点数、状态用 BOOLEAN，缺失数值保留 NULL；街区几何存为 STRING JSON，不依赖 Doris 地理扩展。
- 事实表通过自然键关联维度，便于源字段核验；所有键一致性在装载代码和看板完整性检查中处理，数据库未声明外键。

## 字段与数据边界

字段类型及注释以 DDL 为准。不会装载房源描述、房东姓名/简介/头像、评论者标识、评论文本、设施复合文本、报价抓取字段和未核实估算字段。公开 `host_id` 只作维度连接键，不在 UI 展示；精确源坐标只用于街区聚合。

## 实际数据库状态

Docker Desktop 启动后，`pixi run services-status` 确认 Doris FE、BE 均 Alive。扩展版 DDL 可创建十张表。之后实际执行 `pixi run data-load-hong-kong`，BE 因系统可用内存只有约 396 MB 而触发 `MEM_ALLOC_FAILED`。

失败后只读查询确认：`dim_city` 1 行、`dim_neighbourhood` 18 行、`dim_snapshot` 1 行、`dim_host_snapshot` 1,568 行、`fact_calendar_availability_day` 5,000 行；分类维度、日期维度和评论事实当时为 0 行。`fact_listing_snapshot` 的行数查询再次因内存限制失败，因此不得把其已写入数量当作已核实。当前数据库是第一期的部分装载，不是完整数据集；唯一键允许待资源恢复后从头重跑覆盖。
