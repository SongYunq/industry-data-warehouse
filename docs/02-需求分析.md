本文件说明系统为谁服务、解决哪些业务问题、包含哪些功能、指标如何定义，以及如何判断需求得到满足。具体来源与字段见 [数据来源与数据字典](03-数据来源与数据字典.md)，模型与存储设计由各设计文档负责，工具与版本见 [技术栈与版本](01-技术栈与版本.md)。

本轮业务内容依据 [数据源选取](12-数据源选取.md) 第 2.1、4、5 节整理，只记录已经确定的行业、数据范围和分析方向。候选方案比较与取舍理由保留在该文档中，不在本文件重复。

## 2. 已知约束与依据

- 面向真实行业设计并实现数据仓库，满足业务决策分析需要；本项目已选定国内快递物流的末端揽收与派件场景。
- 完成需求分析、概念设计、逻辑设计、物理设计、实现与可视化分析。
- 数据模型必须体现分层思想；课程举例为 ODS-DWD-DWS-ADS，具体方案待逻辑设计阶段确定。
- 采用真实、可靠且来源可追溯的数据，不人为构造虚假业务数据。
- 支持 macOS 与 Windows 使用；具体系统版本、处理器架构和资源要求待后续验证。
- 工具选型以技术栈文档中的已确认项为准；工具采用不代表其具体功能已经列入需求。

课程依据：[期末大作业要求](课程原始文档/期末大作业要求.pdf)。报告、答辩及材料提交要求统一见 [答辩与交付](11-答辩与交付.md)。

## 3. 项目背景与业务目标

| 项目 | 已明确的内容 |
| --- | --- |
| 行业与具体场景 | 国内快递物流，聚焦上门揽收、末端派件及快递员在途作业 |
| 核心数据基础 | 菜鸟末端快递揽派数据集 `Cainiao-AI/LaDe`，包含 `LaDe-P` 揽收、`LaDe-D` 派件和快递员轨迹数据 |
| 地域范围 | 数据源覆盖上海、杭州、重庆、吉林、烟台五城；具体加载范围以实际获取记录为准 |
| 分析目标 | 围绕单量、履约时效、片区负荷、快递员作业效率和空间轨迹，观察不同城市与作业范围的差异 |
| 预期支持的决策 | 为识别履约薄弱环节、比较运力负荷与作业效率、分析空间作业差异提供依据 |

本项目基于公开的历史业务数据开展分析。数据源选取已完成，不代表原始数据已经下载、字段已经核验，或上述业务问题已得到实际数据验证。来源与数据局限统一见 [数据来源与数据字典](03-数据来源与数据字典.md)。

## 4. 范围与分析需求

### 4.1 已确定的核心范围

- 围绕揽收与派件两类业务开展分析，保留两类业务的区别。
- 以时间、城市、原始片区、快递员和末端建筑／社区等数据属性为分析线索，研究业务量、时效和负荷差异。
- 将包裹业务与轨迹数据纳入核心数据范围，围绕业务记录和在途作业的关系开展分析。
- 聚焦物流履约与运力分析；数据源不含快递运费金额，财务营收分析不纳入当前范围。

### 4.2 分析需求清单

以下编号用于追踪文档 12 已明确的分析方向。表中“范围检查要点”用于后续细化需求，不代表详细指标、测试用例或功能验收已经完成。

| 需求编号 | 业务问题 | 分析内容 | 依赖数据 | 范围检查要点 |
| --- | --- | --- | --- | --- |
| R01 | 揽收与派件业务量在时间和地域上如何分布？ | 单量分布及城市、片区之间的业务量差异 | `LaDe-P`、`LaDe-D` 的包裹、时间与地域属性 | 能区分揽收与派件，并明确每项统计使用的数据范围与时间依据 |
| R02 | 履约时效存在哪些差异，哪些作业环节需要关注？ | 揽收与派件耗时，以及具备预约时间窗记录的履约情况 | 包裹业务记录中的接单、完成及预约时间窗信息 | 耗时起止事件、时间窗适用业务须有源数据依据；分别检查揽收与派件的字段支持情况 |
| R03 | 不同片区的业务负荷、不同快递员的作业效率有何差异？ | 片区负荷、快递员单量与作业效率比较 | 包裹业务记录中的片区、快递员、时间与完成信息 | 明确比较对象与统计范围；负荷和效率的具体计算口径另行确认 |
| R04 | 业务与在途作业在空间上有何分布和差异？ | 收派件位置分布、快递员轨迹及其与业务记录的关系 | 包裹位置与快递员轨迹数据 | 明确坐标、时间与身份字段的来源及关联依据，保留脱敏数据的适用边界 |

### 4.3 多源融合与处理边界

文档 12 已确定保留多源融合方向，但配套来源尚未选定。行政区划、街道商圈、气象、地形、节假日及大促日历等仍属于后续选型与核查范围，本轮不将其展开为已确认的数据依赖或验收要求。

核心来源是静态历史归档数据。文档 12 提及的按历史日期回放用于说明增量演示的可能方式，不代表已经确定每日更新、实时接入或调度方案；具体处理方式在 [数据处理设计](07-数据处理设计.md) 中确认。

## 5. 指标口径

本节是业务指标定义的统一记录位置。目前文档 12 已明确指标方向，但尚未确定可直接实施的计算口径。

| 已明确的指标方向 | 业务含义 | 对应需求 |
| --- | --- | --- |
| 单量 | 观察揽收与派件的业务规模及分布 | R01、R03 |
| 揽收／派件耗时 | 观察接单与完成等业务事件之间的时效差异 | R02 |
| 准时率、超时违约率 | 观察业务完成情况与预约时间窗之间的关系 | R02 |
| 片区负荷、快递员作业效率 | 观察业务在作业片区和快递员之间的分布与效率差异 | R03 |

本轮不填写公式、分母、去重键、统计日期归属、超时阈值或异常处理规则。后续须在实际核验原始字段及适用业务后，再确认完整定义；尤其不能把揽收预约时间窗直接视为派件业务的时效承诺，也不能仅凭接单时间推定存在派单起点。

每项指标确认后，应补齐业务含义、公式、统计对象、时间口径、单位、筛选与排除条件，以及缺失或异常数据如何计入，再分配指标编号。模型和页面通过指标编号引用，不重复维护另一份公式。

## 6. 非功能需求

- 数据量级依据文档 12 的选型记录：核心来源包含千万级包裹业务记录与数千万级轨迹点。该规模描述不是本地实测结果，也不等于已承诺全量加载；详细范围和实际获取情况统一见 [数据来源与数据字典](03-数据来源与数据字典.md)。
- 数据与分析结果须保留来源、获取范围和使用口径，能够追溯至真实原始记录。
- Streamlit 与 Metabase 同时用于分析展示；展示分工见 [分析与可视化设计](08-分析与可视化设计.md)，两端使用本文件统一确认的指标定义。
- 继续遵守 macOS 与 Windows 的使用约束；运行、查询耗时、资源条件及具体版本在实际选定和验证后记录，本轮不填写性能数值。

## 7. 需求验收与变更

本轮完成行业、核心范围和分析方向的同步；尚未执行数据可行性检查或功能验收。R01—R04 将在数据核验与指标口径确认后，关联至 [测试与验收](09-测试与验收.md) 的具体用例，不能仅以存在图表判定需求满足。

需求发生变化时，记录变更原因、受影响的指标／设计／实现和确认结论，并同步工作进度。
